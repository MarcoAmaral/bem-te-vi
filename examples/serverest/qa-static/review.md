## Review plan

- Work product: the "Carrinhos" (cart) section of the ServeRest API documentation, `https://serverest.dev/swagger.json` (OpenAPI 3.0.0, API version 3.2.2, fetched 2026-10-08): `POST /carrinhos`, `GET /carrinhos`, `GET /carrinhos/{_id}`, `DELETE /carrinhos/concluir-compra`, `DELETE /carrinhos/cancelar-compra`, the `requestBodyCarrinho` schema, and the token rule on `POST /login`
- Review type: **technical review** (default for an API schema, stated as a default and not a finding) (§3.2.4)
- Scope / focus: cart rules (one cart per user, no duplicate product, stock reduction, quantity), request and response schemas, status codes and messages. Out of scope: users, products and login beyond what the cart depends on
- Exit criteria: no `Blocker` or `Major` finding open; every documented 4xx response has a stated trigger and a documented body
- Roles: Author → the ServeRest maintainer (not present, owns every status decision); Reviewer and Scribe → this assistant; Manager, Review leader and Moderator → not covered (solo, AI-assisted review)
- Context found: no repository was supplied, so there are no local tests, fixtures or ADRs. The only Tier 1 source is the published OpenAPI document. To ground contradictions between the document and current behaviour, the live API at `https://serverest.dev` was also called on 2026-10-08 with throwaway users, products and carts (all deleted afterwards). That is dynamic testing, outside a pure static review; every finding that rests on a live call says so ("live:"). Accessibility does not apply to an API document and is skipped for that reason

| SR-002 | 2 Ambiguity | Major | `POST /carrinhos` → `400` | One `example` string lists four different failures separated by `\|`: "Não é permitido possuir produto duplicado \| Não é permitido ter mais de 1 carrinho \| Produto não encontrado \| Produto não possui quantidade suficiente". | SR-004 | 4 States and transitions | Major | Whole `Carrinhos` tag; paths | A user may have only **one** cart, and the document defines no operation to change a cart (no `PUT`/`PATCH`; only `POST`, `GET` and two `DELETE`). How a customer adds one more product to an existing cart is therefore unspecified; the only route is to cancel and recreate. A test asserting only on `message` would be wrong for half the 400s | Document two 400 shapes: `{message, …extra}` for business rules and `{"<field path>": "<text>"}` for validation, with the extra keys per message |

## Verdict

The cart section is usable for exploration but not yet a reliable test basis. 14 findings: 0 Blocker, 6 Major (SR-001 to SR-006), 3 Minor (SR-007, SR-008, SR-013), 5 Question (SR-009 to SR-012, SR-014). Six Major findings are open, so the exit criterion "no Blocker or Major open" is **not met**. The strongest item is SR-001: the schema and the running API disagree on the shape of the request body, so anything generated from the schema fails. SR-005 also points at a probable software defect (a string `quantidade` accepted and `quantidadeTotal` returned as `"02"`).
